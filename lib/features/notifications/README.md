# Project Notification Generator

The Flutter inbox reads persisted rows. It does not schedule checks. The hourly
`project-notification-generator` Edge Function handles stalled tasks and task/project
deadlines. Its database helpers and cron job are in
`supabase/migrations/20261010010000_project_notification_generator.sql`.

## Before deployment

The original schema migrations for projects, boards, tasks, activity logs, and
profiles are not in this repository. The new migration checks every column it
uses and aborts before installing helpers if the deployed schema differs. It
also normalizes known lowercase notification values to the uppercase Flutter
format. It changes the notification user foreign key to `public.profiles(id)`
only after checking that every existing notification user has a profile. It
does not delete notification rows.

`SUPABASE_SERVICE_ROLE_KEY` is read only by the Edge Function at runtime. Keep
it out of Flutter, `config/supabase.json`, source control, and screenshots.
The Function also requires `PROJECT_NOTIFICATION_CRON_SECRET`, a long random string.
Its invocation checks that secret before creating a service-role client.
`supabase/config.toml` disables platform JWT verification for this one
Function because pg_cron authenticates with the separate secret header.

## Local or staging manual test

Use a **staging database with the existing SkillTrack base tables**. An empty
`supabase start` database cannot apply these migrations alone because this
repository does not contain the base-table migrations. Install Supabase CLI and
run Docker. Then:

1. Apply both notification migrations to the staging database.
2. Put `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, and
   `PROJECT_NOTIFICATION_CRON_SECRET` in a private environment file outside this repo.
3. Run `supabase functions serve project-notification-generator --env-file <private-file> --no-verify-jwt`.
4. Send a `POST` to `http://127.0.0.1:54321/functions/v1/project-notification-generator`
   with the header `x-notification-cron-secret: <same-secret>` and body `{}`.
   No public button or user-supplied notification payload is accepted.

```powershell
$secret = Read-Host 'Cron secret' -MaskInput
Invoke-RestMethod -Method Post `
  -Uri 'http://127.0.0.1:54321/functions/v1/project-notification-generator' `
  -Headers @{ 'x-notification-cron-secret' = $secret } `
  -ContentType 'application/json' -Body '{}'
```

5. Inspect the JSON count summary. In staging SQL, inspect
   `select type, context_type, unique_key, created_at from public.notifications
   order by created_at desc limit 20;` Run the request twice: the second run
   should report duplicates rather than insert matching keys again.

For sample data, use an **existing staging profile** with an active project,
unarchived board, and unfinished task. Set a task's deadline to the UTC date
three days, one day, or zero days from the test run. For a stalled task, use an
existing task whose latest activity log is at least seven days old, or whose
`updated_at`/`created_at` is that old if it has no logs. Do not use production
records or hard-code a user's UUID in scripts. Toggle each row in
`notification_preferences` to verify its corresponding category.

Pure generator tests run without Supabase or Docker:

```text
node --experimental-strip-types --test supabase/functions/project-notification-generator/generator.test.ts
```

## Production activation

1. Link the Supabase CLI to the intended project and apply the migrations with
   `npx supabase db push`. Review the schema check and any profile-integrity error
   before retrying. The migration schedules `project-notification-generator-hourly`
   with `0 * * * *` (UTC); it safely does nothing until Vault secrets exist.
2. Set the Edge Function secret with
   `npx supabase secrets set "PROJECT_NOTIFICATION_CRON_SECRET=YOUR_LONG_RANDOM_SECRET"`.
   Replace the placeholder with a long random secret. Do not upload
   the local file containing `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY`;
   Supabase injects those variables into deployed Functions.
3. Deploy with `npx supabase functions deploy project-notification-generator`.
4. In the Supabase SQL editor, store the project URL and the **same** random
   secret in Vault:

```sql
select vault.create_secret('https://<project-ref>.supabase.co',
  'project_notification_url');
select vault.create_secret('<same-random-secret>', 'project_notification_cron_secret');
```

5. Check `cron.job` for the active `project-notification-generator-hourly` job and
   `cron.job_run_details` for executions. Invoke the Function manually once
   with the protected header and inspect the summary before relying on cron.

## Scope

There is no real recommendation/resource provider in this codebase. The
scheduled generator does not invent resources or create recommendation
notifications. Future recommendation events must be generated by a trusted
server component; the Flutter client has no notification insertion API. The Flutter inbox,
read status, unread badge, preferences, and routing remain client features.

## Android push delivery

One notification row feeds both channels: the existing Realtime inbox and an
INSERT webhook to the push dispatcher. Flutter never inserts an alert on receipt.
Push defaults to off. The three category switches keep their existing behavior.
Only Android is supported in this phase; other platforms do not initialize push.

### Database and deployment

1. Apply `supabase/migrations/20261020000000_project_push_notifications.sql`
   to the existing database. It adds `push_enabled`, owner-only device RLS, and
   authenticated register/unregister RPCs. It does not rebuild the original schema.
2. Store these values only in Supabase Edge Function secrets:

   - `FIREBASE_PROJECT_ID`
   - `FIREBASE_CLIENT_EMAIL`
   - `FIREBASE_PRIVATE_KEY` (PEM; literal `\n` sequences are supported)
   - `PROJECT_PUSH_WEBHOOK_SECRET` (random, at least 32 characters)

   Use a Firebase service account permitted to send FCM messages
   (`cloudmessaging.messages.create`). The Edge runtime supplies `SUPABASE_URL`
   and `SUPABASE_SERVICE_ROLE_KEY`. Keep credentials outside this repository.
   Load the four secrets from a private file, for example:

   ```powershell
   npx supabase secrets set --env-file C:\secure\skilltrack-push.env
   ```

3. Deploy from the project root:

   ```powershell
   npx supabase functions deploy project-push-notification-dispatcher
   ```

   The function configuration disables JWT verification for this webhook endpoint.
   Every request must instead pass the dedicated secret header.

### Database Webhook: exact Dashboard configuration

In Supabase Dashboard → Database → Webhooks → Create a new hook:

| Setting | Value |
| --- | --- |
| Name | `project-push-notification-dispatcher` |
| Schema / table | `public.notifications` |
| Event | `INSERT` only |
| Method | `POST` |
| Destination | Supabase Edge Function `project-push-notification-dispatcher` |
| URL for an HTTP destination | `https://<project-ref>.supabase.co/functions/v1/project-push-notification-dispatcher` |
| Header | `x-project-push-secret` |
| Header value | The same private value as `PROJECT_PUSH_WEBHOOK_SECRET` |

Keep the existing generator and hourly cron job. No second schedule is required.
The dispatcher reloads the authoritative notification and current preferences,
sends in batches of five, and returns counts only. Confirmed unregistered or
invalid-token errors retire devices; general payload/authentication errors do not.
Webhook retries can repeat an FCM delivery. Android tags/collapse keys reuse the
notification ID; the client deduplicates foreground banners and tap events.
This does not claim exactly-once delivery from the webhook or FCM.

### Client details

- Android package `com.example.skilltrack` matches the existing Firebase config.
- Existing Firebase files and generated Gradle plugin configuration are preserved.
- The channel is `skilltrack_project_notifications` in Flutter, the manifest, and FCM.
- Messaging 17 deprecates registration tokens in favor of FIDs. This implementation
  keeps `getToken`/`onTokenRefresh`/`deleteToken` for the requested HTTP v1
  `message.token` contract and does not mix the FID APIs.
- Context fields are strings. An additional `user_id` field lets the client reject
  banners and taps belonging to a different learner.
- Taps open the existing inbox. Selecting a row continues to use
  `NotificationListViewModel.openNotification`.
- There is no logout action to modify. Session removal cancels listeners and
  invalidates the Firebase token. Once auth is removed, RLS prevents deleting
  another account’s row; stale rows are retired after an invalid-token response.
- A future logout action should unregister while its original session is valid,
  before signing out. Do not introduce a Profile page solely for logout.

### Verification

Client tests use a fake push transport. They cover opt-in, permission denial,
rollback, refresh, repeated sessions, account switching and inbox routing.
Dispatcher tests mock outbound calls and verify the secret, authoritative data,
category preferences, token retirement, batching, pagination and OAuth signing.

After deployment, verify on an Android device with Google Play services:

1. Open Projects and Notifications; verify Realtime, filters and read/unread.
2. Enable push, grant permission, and check one active device row. Resume/reopen
   and confirm it remains one registration.
3. Create a legitimate notification through trusted server code. Check one inbox
   entry and one foreground banner. Background the app and repeat.
4. Tap background and terminated-app notifications; both must open the inbox.
5. Disable push and confirm in-app-only delivery. Disable each category and
   confirm the dispatcher skips it even if an older webhook arrives.
6. Switch learners and verify account isolation. Revoke OS permission and confirm
   the app does not request permission on resume.
7. Real delivery, token rotation and terminated-app behavior require the deployed
   migration, Firebase secrets, webhook, and a Google Play enabled device.
